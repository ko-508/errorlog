## 冒頭まとめ

OpenAI [API](/glossary/api/) の 401 は、[認証](/glossary/認証/)に失敗したことを示します。ただし「[キー](/glossary/キー/)が間違っている」だけを意味するわけではありません。

公式の[エラー](/glossary/エラー/)一覧を見ると、401 は**4種類に分けて説明されています**。認証情報が無効な場合、送った[キー](/glossary/キー/)が正しくない場合、[アカウント](/glossary/アカウント/)が組織に所属していない場合、そして**要求元の IP が許可リストに一致しない場合**です。

重要なのは、**このうち3つは[キー](/glossary/キー/)を作り直しても直らない**ことです。認証情報が無効な場合の説明には、失効した[キー](/glossary/キー/)を使っている、要求先の組織や[プロジェクト](/glossary/プロジェクト/)に割り当てられたものとは別の[キー](/glossary/キー/)を使っている、そして**呼び出している[エンドポイント](/glossary/エンドポイント/)に必要な[権限](/glossary/権限/)を[キー](/glossary/キー/)が持っていない**、という3つの原因が挙げられています。[キー](/glossary/キー/)そのものは有効でも、宛先や[権限](/glossary/権限/)が合っていなければ 401 です。

もう1つ、切り分けを一気に進める性質があります。「Incorrect [API](/glossary/api/) key provided」の文言には、**実際に送られた[キー](/glossary/キー/)が伏字付きで入ります**。これを自分の[キー](/glossary/キー/)と突き合わせて、一致しないなら、調べるべきは[キー](/glossary/キー/)ではなく**その[キー](/glossary/キー/)を送っている場所**です。

したがって最初にやることは、文言がどの種類かを見分けることです。

## エラーの概要

[キー](/glossary/キー/)が正しくない場合の応答は、この形になります。

```json
{
  "error": {
    "message": "Incorrect API key provided: sk-Eyftb***************************************99vW. You can find your API key at https://platform.openai.com/account/api-keys.",
    "type": "invalid_request_error",
    "param": null,
    "code": "invalid_api_key"
  }
}
```

`message` の中の伏字部分に注目してください。先頭と末尾の数文字が見えています。**これは[サーバー](/glossary/サーバー/)が受け取った[キー](/glossary/キー/)**なので、自分が設定したつもりの[キー](/glossary/キー/)と照合できます。

[プログラム](/glossary/プログラム/)から呼んでいる場合、公式の[ソフトウェア](/glossary/ソフトウェア/)開発キットでは `AuthenticationError` として現れます。公式の説明は、[キー](/glossary/キー/)または[トークン](/glossary/トークン/)が無効・期限切れ・失効している、というものです。

文言は主に次の4種類に分かれます。この判別が切り分けの起点になります。

```text
Invalid Authentication                            → 宛先か権限の不一致
Incorrect API key provided: sk-...                → 送られたキーそのものが違う
You must be a member of an organization to use the API → 組織への所属が無い
IP not authorized                                 → 許可リストとの不一致
```

## まず最初に：文言を4つに振り分ける

第一に、文言に伏字の[キー](/glossary/キー/)が含まれているかを見ます。含まれていれば、それが実際に送られた[キー](/glossary/キー/)です。

第二に、その[キー](/glossary/キー/)の先頭と末尾を、自分が使っているつもりの[キー](/glossary/キー/)と突き合わせます。**違っていれば、[キー](/glossary/キー/)の正しさを確認する作業は無意味**です。送信元を探す段階に移ります。

第三に、一致しているなら、宛先と[権限](/glossary/権限/)を疑います。組織や[プロジェクト](/glossary/プロジェクト/)が意図したものか、その[エンドポイント](/glossary/エンドポイント/)を呼べる[権限](/glossary/権限/)があるか。

第四に、IP に関する文言であれば、許可リストの設定を確認します。この場合、[キー](/glossary/キー/)は完全に正しくても通りません。

## よくある原因と解決手順

### 原因1：意図しないキーが送られている

最も多く、そして最も気付きにくい形です。公式にも、古い失効済みの[キー](/glossary/キー/)が手元に残っている場合がある、と挙げられています。

公式の開発キットは、明示的に指定しなければ[環境変数](/glossary/環境変数/)から[キー](/glossary/キー/)を読みます。したがって、設定[ファイル](/glossary/ファイル/)に正しい[キー](/glossary/キー/)を書いていても、**[環境変数](/glossary/環境変数/)側に古い[キー](/glossary/キー/)が残っていればそちらが使われます**。

**Before（[設定ファイル](/glossary/設定ファイル/)だけを確認する）：**

```bash
cat .env.local | grep OPENAI_API_KEY   # 正しいキーが書いてある
python app.py                          # それでも 401
```

**After（実際に読まれている値を確認する）：**

```bash
# シェルの環境変数に古い値が残っていないか
echo "${OPENAI_API_KEY:0:8}...${OPENAI_API_KEY: -4}"

# プログラムから見た値を確認する
python3 -c "
import os
k = os.environ.get('OPENAI_API_KEY', '')
print('env:', k[:8] + '...' + k[-4:] if k else '(未設定)')
"
```

[エラー](/glossary/エラー/)文言の伏字と、ここで出た先頭・末尾が一致すれば、犯人は[環境変数](/glossary/環境変数/)です。一致しなければ、[プログラム](/glossary/プログラム/)内の直書き、設定管理の仕組み、あるいは中継の[プロキシ](/glossary/プロキシ/)が別の[キー](/glossary/キー/)を差し込んでいます。

なお、[キー](/glossary/キー/)の前後に空白や[改行](/glossary/改行/)が混ざっている場合も同じ[エラー](/glossary/エラー/)になります。公式にも、打ち間違いや余分な空白が原因になり得ると書かれています。設定[ファイル](/glossary/ファイル/)からの読み込みでは、末尾の[改行](/glossary/改行/)が残りやすい点に注意してください。

### 原因2：キーは有効だが、組織やプロジェクトが違う

公式の説明に、要求先の組織や[プロジェクト](/glossary/プロジェクト/)に割り当てられたものとは別の[キー](/glossary/キー/)を使っている場合、と明記されています。

現在の[キー](/glossary/キー/)は[プロジェクト](/glossary/プロジェクト/)に紐づきます。一方、対象の資源（アシスタント、[ファイル](/glossary/ファイル/)、微調整済み[モデル](/glossary/モデル/)など）も特定の[プロジェクト](/glossary/プロジェクト/)に属します。**この2つがずれていると、[キー](/glossary/キー/)が有効でも 401 です**。

```bash
# 明示的に組織とプロジェクトを指定して切り分ける
curl -sS https://api.openai.com/v1/models \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "OpenAI-Organization: org-xxxx" \
  -H "OpenAI-Project: proj_xxxx"
```

指定を変えて結果が変わるなら、この形です。公式も、[キー](/glossary/キー/)と組織 [ID](/glossary/id/) を要求[ヘッダー](/glossary/ヘッダー/)で正しく指定するよう案内しており、[プロジェクト](/glossary/プロジェクト/)固有の[キー](/glossary/キー/)は設定画面で対象[プロジェクト](/glossary/プロジェクト/)を選んで確認できると説明しています。

### 原因3：エンドポイントに必要な権限がない

公式の説明の3つ目です。呼び出そうとしている[エンドポイント](/glossary/エンドポイント/)に対して、[キー](/glossary/キー/)が必要な[権限](/glossary/権限/)を持っていない場合も 401 になります。

とくに管理系の[API](/glossary/api/) で起こります。通常の[キー](/glossary/キー/)で組織の管理用[エンドポイント](/glossary/エンドポイント/)を呼ぶと、権限不足として拒否されます。この場合、[キー](/glossary/キー/)の再発行では解決しません。**必要なのは、その[エンドポイント](/glossary/エンドポイント/)向けの種別の[キー](/glossary/キー/)**です。

[キー](/glossary/キー/)には読み取り専用などの制限を設定できるため、書き込み系の操作だけが失敗する、という形でも現れます。読み取りは通るのに作成だけ 401、という状況ならこれを疑ってください。

### 原因4：IP が許可リストに一致しない

公式に「IP not authorized」として明記されている原因です。要求元の IP が、[プロジェクト](/glossary/プロジェクト/)または組織に設定された許可リストと一致しない場合に返ります。

この形は、手元では通るのに配備先で失敗する、という現れ方をします。**[キー](/glossary/キー/)も組織も[権限](/glossary/権限/)もすべて正しいため、いくら確認しても原因に辿り着きません**。

疑うべき状況は明確です。配備先を変えた、実行環境の外向き IP が変わった、あるいは組織側で許可リストが新たに設定された。これらの心当たりがあれば、まず設定を確認してください。

自動で台数が増える構成や、外向き IP が固定されていない[環境](/glossary/環境/)では、許可リストの運用自体を見直す必要があります。

### 原因5：組織に所属していない

公式が独立した項目として挙げている原因です。[アカウント](/glossary/アカウント/)がどの組織にも属していない場合に返ります。

原因として、以前の組織から退出したか外された、[プロジェクト](/glossary/プロジェクト/)から外された、組織自体が[削除](/glossary/削除/)された、という3つが挙げられています。**利用者側の設定ミスではなく、所属の変化**が原因です。

対処は、組織の管理者に招待してもらうか、新しい組織を用意することです。個人で使っていた[キー](/glossary/キー/)が、組織の整理をきっかけに突然使えなくなった場合はこれを疑ってください。

## 補足：似ているが別のもの

利用が許可されていない国や地域からの呼び出しは 403 です。公式では 401 とは別の項目として整理されており、対応するのは対応国の一覧の確認です。

残高や支出の上限に関する[エラー](/glossary/エラー/)は 429 です。公式には、請求関連の[エラー](/glossary/エラー/)では `error.code` を見て具体的な原因を特定するよう書かれており、残高切れ、組織の支出上限、[プロジェクト](/glossary/プロジェクト/)の支出上限、承認された利用上限といった識別子が個別に定義されています。**[認証](/glossary/認証/)の問題ではないので、[キー](/glossary/キー/)を触っても解決しません**。

開発キットの区分では、401 は[認証](/glossary/認証/)の例外、403 は[権限](/glossary/権限/)の例外として別々に定義されています。後者の説明には、正しい[キー](/glossary/キー/)と組織 [ID](/glossary/id/)、資源 [ID](/glossary/id/) を使っているかを確認するよう書かれています。

Azure 経由で同じ[モデル](/glossary/モデル/)を使う場合、[認証](/glossary/認証/)の仕組み自体が別です。[ヘッダー](/glossary/ヘッダー/)の名前も鍵の管理も異なるため、本記事の内容はそのままでは当てはまりません（[Azure の 401 の記事](/posts/azure_401/)）。

他の基盤の 401 とも、応答に入る情報の量が違います（[GCP の 401 の記事](/posts/gcp_401/)）。

## 切り分けの順序

1. 文言に伏字の[キー](/glossary/キー/)が入っているかを見る。入っていれば、それが実際に送られた[キー](/glossary/キー/)。
2. 先頭と末尾を自分の[キー](/glossary/キー/)と突き合わせる。違えば、[キー](/glossary/キー/)ではなく送信元を探す。
3. [環境変数](/glossary/環境変数/)を確認する。設定[ファイル](/glossary/ファイル/)より優先されることがある。
4. 前後の空白や[改行](/glossary/改行/)を確認する。読み込み時に混ざりやすい。
5. 一致しているなら、組織と[プロジェクト](/glossary/プロジェクト/)を明示して切り分ける。
6. 特定の操作だけ失敗するなら、[キー](/glossary/キー/)の[権限](/glossary/権限/)を疑う。管理系は別種の[キー](/glossary/キー/)が要る。
7. 手元では通るのに配備先で失敗するなら、IP 許可リストを確認する。
8. 突然使えなくなったなら、組織への所属の変化を疑う。

## 確認コマンド集

```bash
# 1. 実際に送られているキーの先頭と末尾を確認する
python3 -c "
import os
k = os.environ.get('OPENAI_API_KEY', '')
print(repr(k[:8]), '...', repr(k[-4:]), '| 長さ:', len(k))
"

# 2. 前後の空白や改行が混ざっていないかを見る
printf '%s' "$OPENAI_API_KEY" | od -c | tail -3

# 3. 最小の要求で認証だけを確認する
curl -sS -o /dev/null -w "%{http_code}\n" https://api.openai.com/v1/models \
  -H "Authorization: Bearer $OPENAI_API_KEY"

# 4. エラーの種別と文言を取り出す
curl -sS https://api.openai.com/v1/models \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  | python3 -c "import json,sys; e=json.load(sys.stdin).get('error',{}); print(e.get('code'), '|', e.get('message'))"

# 5. 組織とプロジェクトを明示して切り分ける
curl -sS -o /dev/null -w "%{http_code}\n" https://api.openai.com/v1/models \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "OpenAI-Organization: org-xxxx" \
  -H "OpenAI-Project: proj_xxxx"

# 6. 配備先の外向き IP を確認する（許可リストとの照合用）
curl -sS https://api.ipify.org

# 7. プログラムから見えている値を確認する（開発キット経由）
python3 -c "
from openai import OpenAI
c = OpenAI()
print('sdk key:', (c.api_key or '')[:8] + '...' + (c.api_key or '')[-4:])
"
```

## Editor's Note

この[エラー](/glossary/エラー/)の切り分けを一撃で終わらせる手がかりが、文言の中にあります。それを示す相談が残っています（[401 Incorrect API key provided](https://community.openai.com/t/401-incorrect-api-key-provided/603609)）。

2024年1月、相談者は 401 の文言に伏字の[キー](/glossary/キー/)が出ているのを見て、こう書いています。**「その[キー](/glossary/キー/)は使ったことがないし、自分の[キー](/glossary/キー/)一覧にも存在しない」**。試したことも列挙されています。新しい[キー](/glossary/キー/)の発行、ブラウザの[キャッシュ](/glossary/キャッシュ/)[削除](/glossary/削除/)、設定[ファイル](/glossary/ファイル/)の値と管理画面の[キー](/glossary/キー/)の照合、打ち間違いや空白の確認。

どれも真っ当な確認ですが、**全部[キー](/glossary/キー/)の側を疑っています**。返答は視点を変えるものでした。[キー](/glossary/キー/)はまず基本[ソフトウェア](/glossary/ソフトウェア/)の[環境変数](/glossary/環境変数/)から探されるので、そこに古い値が設定されていないか見てほしい、という指摘です。相談者は数時間後に解決を報告しています。

構造はこうです。文言に出ている[キー](/glossary/キー/)は、[サーバー](/glossary/サーバー/)が受け取った[キー](/glossary/キー/)です。それが自分の知らない[キー](/glossary/キー/)だということは、**知らない場所から別の[キー](/glossary/キー/)が送られている**という意味になります。この時点で、正しい[キー](/glossary/キー/)を何度確認しても無駄だと分かります。探すべきは値ではなく経路です。

同じ相談の後半で、別の回答者がこう整理しています。先の[エラー](/glossary/エラー/)は、呼び出しに使われていた誤った認証情報の**出どころを突き止めたこと**で解決したのだろう、と。

401 に当たったら、まず文言の伏字を読んでください。自分の[キー](/glossary/キー/)と一致するかどうかで、調べる対象が正反対に変わります。
