## 冒頭まとめ

[Docker](/glossary/docker/)の[エラー](/glossary/エラー/)を検索して1件ずつ直しているのに、次の日には別の[エラー](/glossary/エラー/)で止まる。この繰り返しから抜けるには、覚える順序を変える必要があります。

[Docker](/glossary/docker/)の[エラー](/glossary/エラー/)の多くは、4つの境界のどこかで起きています。ホストと[コンテナ](/glossary/コンテナ/)の境界、[イメージ](/glossary/イメージ/)と[コンテナ](/glossary/コンテナ/)の境界、[コンテナ](/glossary/コンテナ/)間の境界、そして書き込み可能レイヤーと永続領域の境界です。[エラー](/glossary/エラー/)文はこの境界のどれで止まったかを示していますが、境界の存在を知らないと文言が読めません。

したがって学ぶ順序は、[コマンド](/glossary/コマンド/)の数ではなく境界の数で決まります。この記事では、[コンテナ](/glossary/コンテナ/)と[イメージ](/glossary/イメージ/)、Dockerfileとビルド、[ポート](/glossary/ポート/)と[ネットワーク](/glossary/ネットワーク/)、ボリューム、Compose、[ログ](/glossary/ログ/)とトラブルシューティングの6段階に分けて示します。

各段階には「次へ進む目安」を置きました。目安を満たさないまま先へ進むと、後の段階の[エラー](/glossary/エラー/)が前の段階の理解不足として現れます。急がずに順に進めてください。

## エラーを個別に直すだけでは理解しにくい理由

検索で見つかる対処は、多くの場合その[環境](/glossary/環境/)で有効だった手順です。なぜ有効だったかは書かれていないことがあります。

たとえば `docker compose down -v` を実行すれば起動時の[エラー](/glossary/エラー/)が消える、という手順があったとします。これはボリュームを削除して[初期化](/glossary/初期化/)し直す操作なので、確かに[エラー](/glossary/エラー/)は消えます。しかし同時にデータも消えます。ボリュームが何であるかを知らないまま実行すると、次は「データが消えた」という別の問題に変わります。

同じことが[ポート](/glossary/ポート/)の公開でも起きます。`-p 8080:80` を `-p 80:80` に変えたら繋がった、という手順は、どちらの数字がホスト側でどちらが[コンテナ](/glossary/コンテナ/)側かを知らなければ再現できません。

[エラー](/glossary/エラー/)文そのものも同じです。[Docker](/glossary/docker/)の[エラー](/glossary/エラー/)は、どの部品が返したのかを示しています。[CLI](/glossary/cli/)が返したのか、[デーモン](/glossary/デーモン/)が返したのか、[コンテナ](/glossary/コンテナ/)の中のプロセスが返したのかで、直す場所が変わります。この区別は、次に説明する全体像を知っていれば読み取れます。

## 最初に理解するべきDockerの全体像

先に部品の関係を押さえます。ここを飛ばすと、後のすべての段階で判断がぶれます。

[Docker](/glossary/docker/)は[クライアント](/glossary/クライアント/)と[サーバー](/glossary/サーバー/)に分かれています。公式ドキュメントによれば、`docker` [コマンド](/glossary/コマンド/)が[Docker](/glossary/docker/)[クライアント](/glossary/クライアント/)で、利用者が最もよく使う操作の入口です。実際の作業は[Docker](/glossary/docker/)[デーモン](/glossary/デーモン/)（`dockerd`）が行い、[イメージ](/glossary/イメージ/)、[コンテナ](/glossary/コンテナ/)、[ネットワーク](/glossary/ネットワーク/)、ボリュームといった[オブジェクト](/glossary/オブジェクト/)を管理します。両者は[REST](/glossary/rest/) [API](/glossary/api/)を使い、UNIXソケットまたはネットワークインターフェース経由で[通信](/glossary/通信/)します。[クライアント](/glossary/クライアント/)と[デーモン](/glossary/デーモン/)は同じマシンで動かすことも、別のマシンに置くこともできます（[Docker overview](https://docs.docker.com/get-started/docker-overview/)）。

この構造から、[エラー](/glossary/エラー/)の読み分けが1つ決まります。`Cannot connect to the Docker daemon` のような文言は、[クライアント](/glossary/クライアント/)が[デーモン](/glossary/デーモン/)へ届いていないという意味です。[コンテナ](/glossary/コンテナ/)の設定を見直しても変わりません。逆に、[コンテナ](/glossary/コンテナ/)の中の[アプリケーション](/glossary/アプリケーション/)が出した[エラー](/glossary/エラー/)は、[Docker](/glossary/docker/)の設定ではなく[アプリケーション](/glossary/アプリケーション/)の問題です。

もう1つの軸が[イメージ](/glossary/イメージ/)と[コンテナ](/glossary/コンテナ/)の関係です。[イメージ](/glossary/イメージ/)は読み取り専用の層の集まりで、[コンテナ](/glossary/コンテナ/)はその上に書き込み可能な層を1つ載せて動かしたものです。公式ドキュメントは、[コンテナ](/glossary/コンテナ/)の中で作られた[ファイル](/glossary/ファイル/)は既定でこの書き込み可能なコンテナレイヤーに[保存](/glossary/保存/)され、そのレイヤーは[コンテナ](/glossary/コンテナ/)ごとに固有だと説明しています（[Data persistence overview](https://docs.docker.com/engine/storage/)）。

この2つの軸、つまり[クライアント](/glossary/クライアント/)と[デーモン](/glossary/デーモン/)の関係、[イメージ](/glossary/イメージ/)と[コンテナ](/glossary/コンテナ/)の関係が、以降のすべての段階の土台になります。

まずは手元の[環境](/glossary/環境/)が動いているかを確認してください。

```bash
docker version
```

出力は[クライアント](/glossary/クライアント/)側と[サーバー](/glossary/サーバー/)側に分かれます。[サーバー](/glossary/サーバー/)側が表示されなければ、[デーモン](/glossary/デーモン/)へ届いていません。この時点で次へ進んでも、以降の[コマンド](/glossary/コマンド/)はすべて失敗します。

## 学習ステップ1：コンテナとイメージ

**何を理解する段階か**：[イメージ](/glossary/イメージ/)が設計図、[コンテナ](/glossary/コンテナ/)がそれを動かした実体であること、そして両者が別々に管理されていることです。

**なぜ[エラー](/glossary/エラー/)解決に必要か**：「[イメージ](/glossary/イメージ/)を更新したのに反映されない」という状況は、古い[コンテナ](/glossary/コンテナ/)が動き続けているだけであることが多くあります。[イメージ](/glossary/イメージ/)と[コンテナ](/glossary/コンテナ/)が別物だと分かっていないと、この判断ができません。

**最低限覚える概念**：[イメージ](/glossary/イメージ/)、[コンテナ](/glossary/コンテナ/)、[コンテナ](/glossary/コンテナ/)の状態（作成済み、実行中、停止）、そして名前と[ID](/glossary/id/)の関係です。

**実際に試す[コマンド](/glossary/コマンド/)**：

```bash
# 手元にあるイメージを一覧する
docker images

# イメージからコンテナを作って起動する
docker run -d --name web nginx

# 実行中のコンテナを一覧する
docker ps

# 停止中を含めて一覧する（-a を付けないと停止中は見えない）
docker ps -a

# コンテナの詳細な設定を確認する
docker inspect web

# 実行中のコンテナの中でコマンドを実行する
docker exec -it web sh
```

`docker ps` と `docker ps -a` の差は重要です。既定では実行中のものしか表示されません。停止した[コンテナ](/glossary/コンテナ/)は見えないまま残り続け、名前を占有します。

**次の段階へ進む目安**：`docker ps -a` の出力を見て、どれが実行中でどれが停止中かを説明できること。`docker inspect` の出力から、その[コンテナ](/glossary/コンテナ/)が使っている[イメージ](/glossary/イメージ/)名を取り出せることです。

**関連して発生しやすい[エラー](/glossary/エラー/)**：`The container name "/web" is already in use by container "..."` は、停止した[コンテナ](/glossary/コンテナ/)が名前を握っている状態です。`No such container` は、指定した名前や[ID](/glossary/id/)の[コンテナ](/glossary/コンテナ/)が存在しない状態を指します。

## 学習ステップ2：Dockerfileとビルド

**何を理解する段階か**：[イメージ](/glossary/イメージ/)がどう作られるか、そして層として積み上がることです。

**なぜ[エラー](/glossary/エラー/)解決に必要か**：ビルド時の[エラー](/glossary/エラー/)と実行時の[エラー](/glossary/エラー/)は別物です。この区別ができないと、`docker run` で直すべきものを `Dockerfile` で直そうとしたり、その逆をしたりします。

**最低限覚える概念**：`Dockerfile` の各命令が層を作ること、ビルド文脈（送られる[ファイル](/glossary/ファイル/)の範囲）、そして[キャッシュ](/glossary/キャッシュ/)が効く条件です。

**実際に試す[コマンド](/glossary/コマンド/)**：

```bash
# カレントディレクトリの Dockerfile からイメージを作る
docker build -t myapp:dev .

# 作られたイメージを確認する
docker images myapp

# キャッシュを使わずに作り直す（原因の切り分けに使う）
docker build --no-cache -t myapp:dev .
```

末尾の `.` はビルド文脈の指定です。ここで指定した範囲の外にある[ファイル](/glossary/ファイル/)は `COPY` できません。「[ファイル](/glossary/ファイル/)があるのにコピーできない」という詰まりは、ここが原因のことがあります。

**次の段階へ進む目安**：`Dockerfile` を1行変えたときに、どこから作り直されるかを説明できることです。

**関連して発生しやすい[エラー](/glossary/エラー/)**：`failed to solve` で始まる文言はビルドの失敗です。`no such file or directory` がビルド中に出た場合は、ビルド文脈の外を参照しています。

## 学習ステップ3：ポートとネットワーク

**何を理解する段階か**：3種類の[ポート](/glossary/ポート/)と、`localhost` が指す先が実行場所によって変わることです。

**なぜ[エラー](/glossary/エラー/)解決に必要か**：「繋がらない」という症状は、この段階の理解不足で起きるものが最も多くなります。

**最低限覚える概念**：

第一に、[コンテナ](/glossary/コンテナ/)内部の[ポート](/glossary/ポート/)です。[コンテナ](/glossary/コンテナ/)の中で動くプロセスが待ち受けている番号で、[コンテナ](/glossary/コンテナ/)の外からは直接見えません。

第二に、ホストへ公開する[ポート](/glossary/ポート/)です。公式ドキュメントによれば、`--publish` または `-p` フラグは、[コンテナ](/glossary/コンテナ/)の[ポート](/glossary/ポート/)を[Docker](/glossary/docker/)ホストの[ポート](/glossary/ポート/)へ対応付ける規則をホスト側に作ります。`-p 8080:80` はホストの8080番を[コンテナ](/glossary/コンテナ/)の80番へ対応付けるという意味で、左がホスト、右が[コンテナ](/glossary/コンテナ/)です（[Publishing and exposing ports](https://docs.docker.com/engine/network/port-publishing/)）。同じページには `-p 192.168.1.100:8080:80` のように、ホスト側の待ち受けアドレスを限定できることも記載されています。

第三に、Compose内のサービス間通信です。これは次の段階で扱います。

そして `localhost` の意味です。[コンテナ](/glossary/コンテナ/)の中で `localhost` と書けば、その[コンテナ](/glossary/コンテナ/)自身を指します。ホストで動く[データベース](/glossary/データベース/)には届きません。逆にホストのブラウザで `localhost:8080` と入力すれば、ホストの8080番を指し、公開設定があれば[コンテナ](/glossary/コンテナ/)へ転送されます。同じ文字列が、書いた場所によって別のものを指します。

**実際に試す[コマンド](/glossary/コマンド/)**：

```bash
# ポートを公開してコンテナを起動する（左がホスト、右がコンテナ）
docker run -d --name web -p 8080:80 nginx

# 公開状況を確認する
docker ps --format '{{.Names}}\t{{.Ports}}'

# Docker が管理しているネットワークを一覧する
docker network ls

# コンテナがどのネットワークに属しているかを確認する
docker inspect web --format '{{json .NetworkSettings.Networks}}'
```

**次の段階へ進む目安**：[コンテナ](/glossary/コンテナ/)の中の[設定ファイル](/glossary/設定ファイル/)に書く接続先と、ホストのブラウザに入力する接続先が違う理由を説明できることです。

**関連して発生しやすい[エラー](/glossary/エラー/)**：`port is already allocated` はホスト側の番号が別のプロセスに使われている状態です。`connection refused` は、届いた先で誰も待ち受けていない状態を指します。

## 学習ステップ4：ボリュームとデータ永続化

**何を理解する段階か**：[コンテナ](/glossary/コンテナ/)を削除すると消えるデータと、残るデータの違いです。

**なぜ[エラー](/glossary/エラー/)解決に必要か**：この区別を知らないまま「作り直せば直る」という対処を続けると、いずれデータを失います。

**最低限覚える概念**：既定では[コンテナ](/glossary/コンテナ/)内で作られた[ファイル](/glossary/ファイル/)は書き込み可能なコンテナレイヤーに[保存](/glossary/保存/)され、そのレイヤーは[コンテナ](/glossary/コンテナ/)ごとに固有です。公式ドキュメントは、このレイヤーからデータをホストや別の[コンテナ](/glossary/コンテナ/)へ取り出すのは容易ではないとも述べています（[Data persistence overview](https://docs.docker.com/engine/storage/)）。

これに対してボリュームは、[Docker](/glossary/docker/)が作成して管理する永続的なデータ保存先です。ボリュームを作ると[Docker](/glossary/docker/)ホスト上の[ディレクトリ](/glossary/ディレクトリ/)に[保存](/glossary/保存/)され、それが[コンテナ](/glossary/コンテナ/)へマウントされます（[Volumes](https://docs.docker.com/engine/storage/volumes/)）。[コンテナ](/glossary/コンテナ/)とは別に管理されるため、[コンテナ](/glossary/コンテナ/)を削除してもボリュームは残ります。

つまり、残したいデータはボリュームに置き、消えてよい一時[ファイル](/glossary/ファイル/)だけをコンテナレイヤーに置く、という設計になります。

**実際に試す[コマンド](/glossary/コマンド/)**：

```bash
# ボリュームを一覧する
docker volume ls

# ボリュームをマウントしてコンテナを起動する
docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16

# コンテナを削除してもボリュームが残ることを確認する
docker rm -f db
docker volume ls

# ボリュームの保存場所などを確認する
docker volume inspect pgdata
```

`docker volume rm` や `docker compose down -v` は、この永続領域を削除する操作です。実行前に、そのボリュームに何が入っているかを `docker volume inspect` と実際の[ディレクトリ](/glossary/ディレクトリ/)で確認してください。`docker system prune -a` も同様で、内容を確認せずに実行すると、必要な[イメージ](/glossary/イメージ/)や[ネットワーク](/glossary/ネットワーク/)まで消えます。

**次の段階へ進む目安**：[コンテナ](/glossary/コンテナ/)を削除して作り直したときに、どのデータが残りどのデータが消えるかを、実際に手を動かして確認できることです。

**関連して発生しやすい[エラー](/glossary/エラー/)**：「再起動したらデータが消えた」という症状は、[エラー](/glossary/エラー/)としては出ません。ボリュームを使っていなかっただけです。逆に「古い設定が残っている」という症状は、消したつもりのボリュームが残っていることがあります。

## 学習ステップ5：Docker Compose

**何を理解する段階か**：Composeが長い[コマンド](/glossary/コマンド/)の短縮ではなく、複数[コンテナ](/glossary/コンテナ/)の構成を宣言する仕組みであることです。

**なぜ[エラー](/glossary/エラー/)解決に必要か**：Composeを使い始めると、[ネットワーク](/glossary/ネットワーク/)とボリュームが自動で作られます。何が自動で作られているかを知らないと、前の2段階で覚えたことが使えません。

**最低限覚える概念**：`compose.yaml` は、どのサービスをどう組み合わせるかを書いたものです。Composeはこれを読んで、必要な[ネットワーク](/glossary/ネットワーク/)、ボリューム、[コンテナ](/glossary/コンテナ/)を作ります。

サービス間通信の仕組みは押さえておいてください。公式ドキュメントによれば、Composeは既定で[アプリケーション](/glossary/アプリケーション/)用の[ネットワーク](/glossary/ネットワーク/)を1つ作り、各サービスの[コンテナ](/glossary/コンテナ/)をそこへ参加させます。[ネットワーク](/glossary/ネットワーク/)名は `<プロジェクト名>_default` で、各サービスは自分の名前を内部の[DNSサーバー](/glossary/dnsサーバー/)へ登録するため、[コンテナ](/glossary/コンテナ/)同士はサービス名で直接到達できます。[IPアドレス](/glossary/ipアドレス/)の指定や手動の設定は不要です（[Networking in Compose](https://docs.docker.com/compose/how-tos/networking/)）。

同じページには、`web` と `db` という2つのサービスがある場合、`web` は `postgres://db:5432` で[データベース](/glossary/データベース/)へ接続でき、ホストからは公開設定に応じて `postgres://localhost:8001` でアクセスできる、という例が示されています。ここが前段階の `localhost` の話と繋がります。[コンテナ](/glossary/コンテナ/)間はサービス名、ホストからは公開した[ポート](/glossary/ポート/)です。

さらに、[コンテナ](/glossary/コンテナ/)の[IPアドレス](/glossary/ipアドレス/)は[ネットワーク](/glossary/ネットワーク/)のサブネットから起動のたびに動的に割り当てられ、再起動や再作成をまたいで保持されないため、IPではなく名前で参照するように、とも書かれています。

[プロジェクト](/glossary/プロジェクト/)名は既定で[ディレクトリ](/glossary/ディレクトリ/)名から取られます。別の場所にある同名の[ディレクトリ](/glossary/ディレクトリ/)で作業すると、同じ[プロジェクト](/glossary/プロジェクト/)として扱われます。`--project-name` フラグまたは `COMPOSE_PROJECT_NAME` [環境変数](/glossary/環境変数/)で上書きできます。

**実際に試す[コマンド](/glossary/コマンド/)**：

```bash
# 構成を起動する（-d はバックグラウンド実行）
docker compose up -d

# 解釈後の構成を確認する（変数展開後の内容が見える）
docker compose config

# 構成に含まれるコンテナの状態を確認する
docker compose ps

# 停止して、作られたコンテナとネットワークを削除する
docker compose down
```

`docker compose down` は既定でボリュームを削除しません。削除するには `-v` を付けます。この違いは前段階の内容と直結します。

**次の段階へ進む目安**：`compose.yaml` を読んで、起動後に何個の[コンテナ](/glossary/コンテナ/)と何個の[ネットワーク](/glossary/ネットワーク/)が作られるかを、実行前に言えることです。

**関連して発生しやすい[エラー](/glossary/エラー/)**：`Conflict. The container name ... is already in use` は、同じ[プロジェクト](/glossary/プロジェクト/)名の古い[コンテナ](/glossary/コンテナ/)が残っている場合に起きます。サービス間の接続で `could not translate host name` のような名前解決の失敗が出る場合は、接続先にサービス名ではなく `localhost` を書いている可能性があります。

## 学習ステップ6：ログ確認とトラブルシューティング

**何を理解する段階か**：[エラー](/glossary/エラー/)が出たときに、どの順番で何を見るかです。

**なぜ[エラー](/glossary/エラー/)解決に必要か**：ここまでの5段階は、この順序を実行するための前提知識です。順序が決まっていれば、初めて見る[エラー](/glossary/エラー/)でも調べる範囲を絞れます。

**確認の順序**：

第一に、実行した[コマンド](/glossary/コマンド/)そのものを確認します。打ち間違い、[ディレクトリ](/glossary/ディレクトリ/)の取り違え、オプションの位置の誤りは、この時点で見つかります。

第二に、表示された[エラー](/glossary/エラー/)全文を読みます。要約された1行だけでなく、その下の行まで含めてです。[Docker](/glossary/docker/)の[エラー](/glossary/エラー/)は、どの部品が返したかを示す情報を含んでいます。

第三に、対象[コンテナ](/glossary/コンテナ/)の状態を確認します。実行中なのか、停止しているのか、そもそも作られていないのかで、次に見る場所が変わります。

```bash
docker ps -a
docker inspect <コンテナ名> --format '{{.State.Status}} {{.State.ExitCode}}'
```

第四に、[ログ](/glossary/ログ/)を見ます。[コンテナ](/glossary/コンテナ/)の中のプロセスが出力した内容はここに集まります。

```bash
# 直近の100行を表示する
docker logs --tail 100 <コンテナ名>

# 時刻を付けて追従表示する
docker logs -f -t <コンテナ名>
```

第五に、[ポート](/glossary/ポート/)、[ネットワーク](/glossary/ネットワーク/)、ボリュームを確認します。ここまでで原因が分からない場合、接続経路か保存先に問題があります。

```bash
docker ps --format '{{.Names}}\t{{.Ports}}'
docker network ls
docker volume ls
```

第六に、[Docker](/glossary/docker/)[デーモン](/glossary/デーモン/)側の状態を確認します。個別の[コンテナ](/glossary/コンテナ/)ではなく、[Docker](/glossary/docker/)自体が正常かどうかを見ます。

```bash
docker info
docker version
```

`docker version` で[サーバー](/glossary/サーバー/)側が表示されない場合、ここまでの確認は意味を持ちません。[デーモン](/glossary/デーモン/)への接続から見直してください。

**次の段階へ進む目安**：初めて見る[エラー](/glossary/エラー/)に対して、この6段階のどこから調べるかを即座に決められることです。

**避けるべき対処**：[権限](/glossary/権限/)の[エラー](/glossary/エラー/)に対して `chmod 777` を当てる、[Docker](/glossary/docker/)ソケットへ無制限の[権限](/glossary/権限/)を与える、`docker system prune -a` を内容の確認なしに実行する、[ファイアウォール](/glossary/ファイアウォール/)を無効にする、[本番環境](/glossary/本番環境/)で[ポート](/glossary/ポート/)を無条件に全公開する、といった手順は、症状を消しても原因を残します。特に後ろの3つは、失ったデータや開いた経路を後から戻せません。

## 独学と動画講座の使い分け

ここまでの6段階は、公式ドキュメントと手元の[環境](/glossary/環境/)だけでも進められます。実際、この記事で参照した仕様はすべて公式ドキュメントに書かれています。

独学が向いているのは、目的が明確な場合です。特定の[エラー](/glossary/エラー/)を直す、特定の機能の仕様を確認する、といった作業は、公式ドキュメントを直接読むのが最短です。

一方で、独学では順序を組み立てる部分が自分の負担になります。何を先に学ぶべきか、どこまで理解したら次へ進んでよいかを、自分で判断し続ける必要があります。この記事はその順序を示すために書いていますが、実際に手を動かす部分は残ります。

動画講座は、この順序と手を動かす部分がまとめて用意されている点が違います。環境構築から演習までが一続きになっているため、途中で詰まって止まる回数を減らせます。反面、自分に必要な部分だけを選んで進めるのは難しくなります。

どちらが適しているかは、いま何に時間を取られているかで決まります。仕様が分からなくて止まっているなら公式ドキュメント、何から手を付けるか決められなくて止まっているなら講座、という切り分けが実際的です。

## 学習後に自力で確認できるようにしたいこと

到達点を具体的に置いておきます。以下を自分の[環境](/glossary/環境/)で確認できるようになっていれば、この記事の範囲は終わりです。

`docker version` の出力から、[クライアント](/glossary/クライアント/)と[サーバー](/glossary/サーバー/)のどちらで問題が起きているかを判断できる。`docker ps -a` の出力から、停止中の[コンテナ](/glossary/コンテナ/)が名前を占有している状況を見つけられる。`-p` の左右がどちらを指すかを説明でき、[コンテナ](/glossary/コンテナ/)の中から見た `localhost` とホストから見た `localhost` の違いを説明できる。[コンテナ](/glossary/コンテナ/)を削除したときに消えるデータと残るデータを、実際に試して確認できる。`compose.yaml` を読んで、作られる[コンテナ](/glossary/コンテナ/)と[ネットワーク](/glossary/ネットワーク/)の数を実行前に言える。初めて見る[エラー](/glossary/エラー/)に対して、[コマンド](/glossary/コマンド/)、[エラー](/glossary/エラー/)全文、[コンテナ](/glossary/コンテナ/)の状態、[ログ](/glossary/ログ/)、[ネットワーク](/glossary/ネットワーク/)とボリューム、[デーモン](/glossary/デーモン/)の順で調べられる。

これらは知識の暗記ではなく、手を動かして確認する操作です。読んだだけでは身に付かない部分なので、手元の[環境](/glossary/環境/)で1つずつ試してください。

## まとめ

[Docker](/glossary/docker/)の[エラー](/glossary/エラー/)が繰り返し起きるのは、[コマンド](/glossary/コマンド/)を知らないからではなく、境界を知らないからです。ホストと[コンテナ](/glossary/コンテナ/)、[イメージ](/glossary/イメージ/)と[コンテナ](/glossary/コンテナ/)、[コンテナ](/glossary/コンテナ/)同士、そして消えるデータと残るデータ。この4つの境界を押さえると、[エラー](/glossary/エラー/)文の読み方が変わります。

学ぶ順序は、[コンテナ](/glossary/コンテナ/)と[イメージ](/glossary/イメージ/)、Dockerfileとビルド、[ポート](/glossary/ポート/)と[ネットワーク](/glossary/ネットワーク/)、ボリューム、Compose、トラブルシューティングです。それぞれに「次へ進む目安」を置いたのは、飛ばした段階が後から別の顔で現れるからです。

公式ドキュメントは仕様の確認先として最も確実です。一方で、学ぶ順序を自分で組み立てる負担が大きいと感じる場合は、順序と演習がまとまった教材を使う選択肢もあります。
