# ErrorLog 編集コンテキスト

errorlog.jp（日本語の技術エラー解決サイト、Hugo/PaperMod）の記事を生成するための編集基準。この文書だけで自己完結する。会話履歴を参照せず、以下の指示に従うこと。

---

## 0. 優先順位

判断が衝突した場合、この順序で決める。

1. **事実の正確性** — 誤った技術情報を載せることは、エラー解決サイトとして最も避けるべき失敗。分量・体裁・締切より優先する。
2. **対象範囲の明確さ** — 既存記事と重複せず、どの現象を扱うかが冒頭で確定していること。
3. **診断の有用性** — 読者が「次に何を確認するか」を決められること。
4. **安全性** — 破壊的操作・検証の無効化を無批判に勧めない。
5. **自然な日本語** — 翻訳調・冗長・語尾の単調さを避ける。
6. **網羅性** — 4以下を犠牲にしてまで原因を増やさない。
7. **書式** — 上記すべてを満たしたうえで型に合わせる。

**根拠が取れない内容は書かない。** 分量が足りなくなる場合、水増しではなく「未確認」と明示するか、その節を削る。

## 1. 記事の役割

### 想定読者と状況

読者は、エラーメッセージをそのまま検索してこの記事に来る。実務の途中で手が止まっており、**今まさに動かない環境を目の前にしている**。学習目的ではない。前提知識は「そのツールを業務で使っている」程度で、内部実装の知識はない。

多くの場合、読者は既に次のいずれかの状態にある。

- エラー文言を読んだが、何を意味するか分からない
- 文言を素直に受け取った結果、見当違いの場所を調べている
- 検索で出てきた回避策を試したが直らない、または直った理由が分からない

### 読了後にできるようになること

**原因の特定ではなく、切り分けの一手目が決まること**が最低ラインである。読者が自分の状況を記事内のどの分岐に当てはめればよいか判断でき、次に打つコマンドが決まっていればよい。すべての原因を網羅する必要はない。

### 他の情報源との役割の違い

- **公式ドキュメント**は仕様を網羅するが、「その文言が出たとき何を疑うか」の順序は書かれていない。ErrorLog はその順序を提供する。
- **一般的な解説記事・Q&A サイト**は回避策を提示するが、なぜそれで直るのか、いつ直らないのかを説明しない。ErrorLog は**文言の出どころと構造**から説明する。
- **既存の ErrorLog 記事**とは、扱う現象・発生層・コードで排他になるよう境界を明示する。

### 情報密度

本文4,000〜5,700字（コードブロック除く、空白除く）。原因は4〜6個。1原因あたり150〜400字＋コマンドまたは設定例。

**薄いと判断する基準**：原因が3個以下、Editor's Note に一次資料の裏付けがない、確認コマンド集が5個未満、原因説明が「〜を確認してください」で終わり何を見るか書いていない。

**厚すぎると判断する基準**：同じ内容を節をまたいで繰り返している、一般論（HTTP の仕組み、コンテナとは何か）に字数を使っている、原因が7個以上で互いに重複している。

## 2. 調査と根拠のルール

### 充足条件（必須）

1記事につき以下をすべて満たすこと。満たせない項目があれば、記事末尾ではなく**執筆前に報告**する。

- **公式一次資料 3本以上**
- **Editor's Note 用の実事例 1本以上**
- **隣接する別コード・別状態との境界を示す資料 1本以上**

すべて URL を取得し、本文を照合したもののみ計上する。検索結果のスニペットだけで計上してはならない。

### 情報源の優先順位

1. **実装コード** — エラー文言がどこで生成されるかを特定できる。最も強い根拠であり、記事の軸はここから立つことが多い。`raw.githubusercontent.com` から直接取得する（kubernetes/kubernetes、moby/moby、openssh/openssh-portable、docker/cli、openai/openai-python など）。
2. **公式ドキュメント** — 既定値、仕様、推奨対処。`raw.githubusercontent.com` 上の docs リポジトリ（kubernetes/website の `content/en/docs` 配下、docker/docs の `content` 配下、github/docs）から取得すると、レンダリング済みページより確実かつ軽い。
3. **公式 API** — 動的に変わる値（鍵の指紋、制限値）は API から取得できる場合がある。ただしレート制限に注意。
4. **公式 Issue / 公式コミュニティ** — 実事例と、公式側の回答。Editor's Note の主材料。
5. **第三者の記事・ブログ** — 記事の根拠としては使わない。存在の傍証にとどめる。

### 取得方法

`web_search` はトークン消費が大きい。**公式リポジトリの生ファイルを `curl` し、`grep` で該当箇所を絞る方式を優先する。** `web_search` は、どのファイルを見るべきか分からない場合と、実事例を探す場合に限る。

GitHub Issue の内容確認は、API がレート制限に当たりやすいため、HTML を `curl` して `grep` する方式が確実。

### URL と主張の対応

各主張は、それを裏付ける資料と1対1で対応していなければならない。**同じページ内の別セクションを取り違えない。** 具体例として、指標の定義がデバッグ用ドキュメントに載っていると思い込んで帰属を誤った事例がある。該当語がそのページに存在するか `grep` で確認してから帰属させる。

同じ資料から複数の事実を引く場合、重複して取得しない。1回取得して必要箇所をすべて抽出する。

### 推測・経験則・再現結果の区別

- **公式に明記がある**：「公式文書には〜と明記されています」「実装では〜と定義されています」
- **実装から読み取れるが文書化されていない**：「実装を読むと〜」（挙動として述べる。仕様として断定しない）
- **報告例から観察される**：「〜という報告があります」「〜という状況が起こります」
- **未確認**：書かない。どうしても触れる必要があれば「執筆時点で一次資料を確認できていない」と明示する。

### 断定してはいけない事項

- エラー応答の `code` / `type` / `param` / `message` の具体値 — 必ず実物を照合する。**実在しない payload を作文しない。** 過去に、下書きが実在しない組み合わせを載せていた事例が複数ある。
- 既定値・閾値・上限値の数値
- あるコードが返るか返らないか（「返らない」と書くには、公式一覧に項目がないこと、SDK に対応する例外クラスがないこと、実報告が見つからないことなど複数の根拠を揃える）
- バージョンによる挙動の違い

### Editor's Note に採用できる根拠

- 公式リポジトリの Issue / PR
- 公式ブログ・公式発表
- 公式コミュニティで、提供元の担当者が回答している記録
- 著名なプロダクトのリポジトリの Issue（現象の実在と再現条件が具体的に記録されているもの）

採用時は、**日付・状態（クローズ済みか）・環境（バージョン）を確認**する。過去の挙動を現在の挙動として書くと誤情報になる。クローズ済みで挙動が変わっている場合、**過去形で書き、現行の挙動を併記する**。

## 3. 対象範囲と既存記事との境界

### 発生層の特定

**「誰がその応答を返したか」を最初に確定させる**のが、このサイトの中心的な診断軸である。多くの記事がこの軸で組み立てられている。

判定材料の例：

- 応答本文の形式（JSON か HTML か、`error` オブジェクトか `detail` 配列か）
- 応答に含まれる識別情報（ヘッダー、末尾の事業者名）
- ログの文言（アクセスログとエラーログで別々に記録される）
- 状態コードとメッセージの組み合わせ

### 似た表示の別エラーとの区別

以下は実際に確認された区別の例であり、同種の判断を他のテーマにも適用する。

- 同じ文言が別のコードで返る場合がある（過負荷を示す文言が、429 と 503 の両方で使われる）
- 同じコードが別の意味を持つ場合がある（409 が「既に存在する」と「同時実行の衝突」に分かれる）
- 文言が原因を説明していない場合がある（退避の文言に並ぶ使用量は、選定過程の記録であって原因ではない）
- クライアント側の例外名は、発生源を示さない（SDK が状態コードから機械的に決めているだけ）

### 新規記事にするか、既存記事に統合するか

**新規にする条件**：発生する層が違う、対処が正反対、検索される文言が明確に別。

**統合すべき条件**：同じ現象の別段階にすぎない、原因と症状の関係にある、内容が互いにほぼ同じになる。

**共食いを避ける**：既存記事が同じ検索クエリを狙っている場合（frontmatter の `top_queries` で確認できる）、新規記事は**別の切り口**を立てる。例として、汎用記事が「どのタイマーで時間切れになったか」を扱っているのに対し、派生記事は「アクセスログでどちらが返したかを判定する」に特化した事例がある。切り口を変えられないなら、新規記事を作らず既存記事の強化を提案する。

**着手前に必ず確認する**：出力ディレクトリに未把握の原稿がないか、サイトに同名記事が公開されていないか、内容が近い既存記事が何をカバーしているか。

### 原因の分類粒度

- 原因同士は**対処が異なる**単位で分ける。同じ対処になるなら統合する。
- 「よくある誤解」「切り分けの失敗」を原因の1つとして立ててよい。実際に多くの記事で最終原因が「別のコードの問題を、このコードとして調べている」になっている。
- 各原因の見出しは、状態を述べる形にする（「〜が〜している」「〜を〜していない」）。手段や対処を見出しにしない。

## 4. 標準フォーマット

### front matter（11項目、順序固定）

```
title: "<ツール名> の <エラー> ：原因と解決策"
date: <YYYY-MM-DD>
description: "<3〜4文>"
tags: ["<ツール名>"]
errorCode: "<コードまたはエラー名>"
lastmod: <YYYY-MM-DD>
service: "<サービス名>"
error_type: "<errorCode と同じ値>"
components: ["<構成要素>", ...]
related_services: ["<関連サービス>", ...]
trend_incident: false
```

- **date**：新規作成なら作成日。既存記事の書き直しなら**元の公開日を維持**し、`lastmod` のみ更新する。未公開の下書きを初公開する場合は公開日を入れてよい。
- **errorCode / error_type**：状態コードなら `"429"`、名前付きエラーなら `"CreateContainerConfigError"` のようにそのまま入れる。両項目に同じ値を入れる。
- **components / related_services**：空にしない。具体的な構成要素名を入れる（例：`["kubelet", "Node"]`、`["Engine", "Networking"]`、`["Chat Completions", "Rate Limits"]`）。
- **top_queries**：既存の下書きに存在する場合は引き継ぐ。新規には自分で追加しない。
- `draft: true` は出力に含めない。

### タイトル

`<ツール名> の <エラー文言またはコード> ：原因と解決策` を基本形とする。エラー文言は原文（英語）のまま。

### description

3〜4文。**記事の軸を要約する**。「〜の原因と対処法を解説します」のような内容のない文にしない。最も重要な事実（誤解の訂正、2系統への分岐、公式に定義がないこと）を含める。

### ## 冒頭まとめ

**目的**：記事の軸を提示し、読者の誤解をここで解く。

**必ず含める**：その文言を誰が出しているか。系統がいくつあるか。最も多い誤解と、その訂正。判断の起点（どこを読めばよいか）。

**書いてはいけない**：一般論（「エラーが出たら焦らず確認しましょう」）、記事の構成説明（「本記事では〜を解説します」）、前置き。

**長さ**：400〜700字。太字は1〜3箇所、核心の主張のみ。

### ## エラーの概要

**目的**：実物のエラー出力を示し、どこを読むかを教える。

**必ず含める**：実際の応答またはログの例（照合済みのもの）。読むべき箇所の指示。複数系統があるなら、系統ごとに例を並べて対比する。

**書いてはいけない**：作文した payload。原因の説明（次節の役割）。

**長さ**：300〜600字＋コードブロック2〜3個。

### ## まず最初に：〜

**目的**：全原因に入る前の共通の切り分け。

**形式**：「第一に、〜」「第二に、〜」の4段構成。各1〜3文。

**必ず含める**：最初に読むべき値（`type`、`reason`、`param`、条件の値、ログの文言）。それによって調査先がどう分かれるか。

**書いてはいけない**：原因ごとの詳細（次節の役割）。長いコマンド列。

**長さ**：200〜350字。

### ## よくある原因と解決手順

`### 原因1：〜` 〜 `### 原因5：〜`（4〜6個）。書き方は第5節を参照。

### ## 補足：似ているが別のもの

**目的**：この記事の対象外を明示し、読者を正しい記事へ送る。

**必ず含める**：隣接するコード・状態との違いを、**判別方法とともに**述べる。既存記事への内部リンク。

**書いてはいけない**：単なる関連記事の羅列。「〜もあります」だけで違いを説明しない書き方。

**長さ**：300〜500字。

### ## 切り分けの順序

**目的**：記事全体を、実行順の手順に圧縮する。

**形式**：番号付きリスト8項目。各1〜2文、命令形または断定。

**必ず含める**：最初の分岐が最初に来ること。危険な操作は後ろに置き、条件を付ける。

**書いてはいけない**：本文にない新情報。

### ## 確認コマンド集

**形式**：単一の bash コードブロック。各コマンドの前に `# 1. 目的` の番号付きコメント。5〜8個。

**必ず含める**：診断コマンドを先に、変更を伴うコマンドを後に。プレースホルダーは `<名前>` 形式の日本語または英語。

**書いてはいけない**：本文で触れていないコマンド。破壊的操作を無警告で置くこと。

### ## Editor's Note

第8節を参照。

### 免責事項

本文の最後に `---` を置き、その後に定型の斜体文を置く。

```
*免責事項：本記事の内容は、執筆時点の公開情報をもとに作成したものです。[ソフトウェア](/glossary/ソフトウェア/)の仕様は予告なく変更されることがあります。最新の情報は各[ツール](/glossary/ツール/)の公式サポートページをご確認ください。本記事の情報を利用した結果生じたいかなる損害についても、著者および運営者は責任を負いかねます。*
```

### 参考資料

独立した節としては置かない。出典は Editor's Note と本文中に markdown リンクで埋め込む。

### 内部リンク

- **用語集リンク**：本文中の該当語に `[語](/glossary/語/)` を張る。**ページが実在する語のみ**。存在しないことが確認済みの語：プロセス、カーネル、ソケット、ボリューム、ノード、データ、サービス、ライブラリ、フレームワーク、アドレス、スクリプト、Pod、リンク、設備。これら以外も、使用前に実在を確認する。
- **記事間リンク**：`[<ツール> の <コード> の記事](/posts/<スラッグ>/)` 形式。**公開済みの記事にのみ張る**。未公開記事へのリンクは作らない。

## 5. 原因別セクションの型

各 `### 原因N：〜` は、原則として以下の順序で書く。

1. **どの状態を指すか** — 1〜2文で状態を定義する。「〜の場合です」
2. **なぜそうなるか** — 実装または公式仕様に基づく短い説明。ここに一次資料の裏付けを置く。
3. **判断材料** — その原因だと判断できる観察点（文言、値、ログ）
4. **確認または修正の手段** — コマンド、設定例、または Before/After
5. **注意点** — 効かない対処、副作用、再発条件

**Before/After 形式**は、設定や実装の変更を示す場合に使う。1記事に1〜2組。

```
**Before（<問題のある状態の説明>）：**

<コードブロック>

**After（<正しい状態の説明>）：**

<コードブロック>
```

Before 側には**なぜ通らないか**をコメントまたは直後の文で示す。After 側は最小限の変更にとどめる。

**最後の原因には、切り分けの誤りを置くことが多い。** 「別のコードの問題をこのコードとして調べている」「例外名で発生源を判断している」「回避策で検証を無効化している」など。これは対処ではなく進め方の指摘であり、記事の軸を再確認する役割を持つ。

## 6. コマンドとコード例のルール

### 掲載条件

- 本文で説明した判断を、実際に確認できるものに限る
- 出力のどこを見るかが説明できるものに限る
- 環境依存が強い場合は、その旨を添える

### プレースホルダー

`<Pod名>`、`<名前空間>`、`<コンテナ>`、`<ARN>`、`<ノード名>` のように山括弧で囲む。実在しそうな値を埋め込まない。

### 出力例

読むべき箇所が複数ある場合、または文言の形が診断材料になる場合に載せる。載せるときは、**どの欄を見るかを直後に明示**する。作文した出力を載せない。

### 危険な操作の扱い

以下は**無警告で提示しない**。提示する場合、影響範囲と条件を必ず添える。

- 常駐プロセス・デーモンの再起動（稼働中の処理に影響する）
- Pod・コンテナ・リソースの強制削除
- 検証の無効化（ホスト鍵検証の無効化、証明書検証の無効化）
- 一括削除（フィルタで絞ったつもりが広く当たる形）

**検証を無効化する回避策は、独立した原因として立て、明示的に推奨しない扱いにする…921 tokens truncated…記事内で統一する。同じ概念を途中で別語に言い換えない。

### 太字

核心の主張にのみ使う。1節あたり0〜2箇所。多用すると強調が機能しなくなる。

## 8. Editor's Note の基準

### 目的

本文が「どう対処するか」を扱うのに対し、Editor's Note は**なぜその誤解が生まれるのか、なぜその設計になっているのか**を、実在の記録で裏付ける。読者が構造を理解し、次に似た状況でも自力で判断できるようにする。

### 入れる条件

- 記事の軸（誤解の訂正、系統の分岐、発生源の判定）を裏付ける実在の記録がある
- その記録が、記事の主張を具体的な数値・文言・やり取りで示している

### 入れないほうがよい条件

- 一次資料の裏付けがなく、一般論になる場合
- 記事の軸と無関係の雑学
- 単なる歴史紹介

**根拠が用意できないなら、Editor's Note を省くほうがよい。** 水増しは品質低下と判断する。

### 優先する材料

1. **記事の軸を直接裏付ける Issue / 報告** — 最優先。特に、提供元の担当者が回答しているもの、複数年にわたり同じ誤解が繰り返し報告されているもの。
2. **公式の発表・障害史** — 事象の規模と正当性を示せる場合。
3. **設計背景** — 実装や仕様の記述から読み取れる意図。

### 書き方

- 冒頭1文で、この節が扱う構造を提示する。
- 記録の内容を、日付・環境・具体的な数値や文言とともに述べる。**引用ではなく要約**で書く。
- 記録から読み取れる原則を、記事の軸に接続して締める。
- 過去にクローズされた記録は**過去形で書き、現行の挙動を併記**する。

**長さ**：600〜1,000字。段落4〜6個。

**URL の対応**：`[記録の題名](URL)` 形式で、言及する記録ごとにリンクを張る。1つの Editor's Note に2件までを目安とする。2件目は補助的な位置づけにする。

## 9. 修正履歴から得られた恒久ルール

以下はすべて、実際に発生した問題とその対処である。全記事に適用する。

### 9.1 実在しないエラー例の混入

**問題**：下書き記事に、実在しない `code` / `type` の組み合わせが載っていた（クォータ超過を別の型として記載、モデル未検出を誤ったコードで記載、存在しない検証エラーコードなど）。

**方針**：応答例は必ず実物を照合してから載せる。照合できないなら、その例を載せない。

**適用**：全分野。

### 9.2 コードの取り違え

**問題**：ある記事が、他のコードで返る事象を自分のコードの原因として列挙していた（残高不足・モデル未検出・キー失効を、地域制限のコードの原因として記載）。

**方針**：原因を列挙する前に、そのコードで実際に返る事象かを公式一覧で確認する。返らないものは「似ているが別のもの」に移し、正しいコードを示す。

**適用**：全分野。特に状態コード記事。

### 9.3 出典の帰属誤り

**問題**：指標の定義が載っているページを取り違えて帰属した。

**方針**：帰属する前に、その語が対象ページに実在するか `grep` で確認する。

**適用**：全分野。

### 9.4 過去の挙動を現在として記載

**問題**：Editor's Note に採用した Issue が古く、現行実装では挙動が修正されていた。

**方針**：採用する記録の日付・クローズ状態・対象バージョンを確認する。修正済みなら過去形で書き、現行の挙動を実装で確認して併記する。

**適用**：全分野。

### 9.5 断定の行き過ぎ

**問題**：「権限不足でこのコードが返ることはない」「上限の話は必ずこのコードである」といった言い切りが、公式に文書化された例外と矛盾していた。

**方針**：原則と例外の二段構えで書く。例外が公式に記載されている場合は必ず併記する。

**適用**：全分野。

### 9.6 記事内の自己矛盾

**問題**：冒頭で「待っても直らない」と書きながら、本文で再試行を推奨していた。

**方針**：執筆後、冒頭まとめと各原因の主張が矛盾していないか確認する。特に「再試行が有効か」「待てば直るか」は記事内で一貫させる。

**適用**：全分野。

### 9.7 既存記事との共食い

**問題**：既存の汎用記事が同じ検索クエリを狙っているのに、内容の近い派生記事を作った。

**方針**：着手前に既存記事の `top_queries` と扱っている原因を確認し、切り口を変えられない場合は新規作成しない。

**適用**：全分野。

### 9.8 二重執筆

**問題**：既に完成原稿が存在する記事を、把握せずに書き始めた。

**方針**：着手前に出力ディレクトリとサイトの公開状況を必ず確認する。

**適用**：全分野。

### 9.9 未確認事項の扱い

**方針**：確認できなかった項目は、報告時に明示する（日付、クローズ状態、特定の実装の文面など）。本文には書かない。

**適用**：全分野。

### 9.10 存在しない用語集リンク

**問題**：用語集にページのない語にリンクを張っていた。

**方針**：使用前に実在を確認し、404 の語は通常表記にする。

**適用**：全記事。

## 10. 良い例と悪い例

### 冒頭

**悪い**：
> Docker を使っていると `port is already allocated` というエラーに遭遇することがあります。本記事では、このエラーの原因と解決方法について詳しく解説します。

一般論と構成説明だけで、情報がない。

**良い**：
> `port is already allocated` を見たとき、多くの人は「そのポートで何かが待ち受けている」と考えます。しかし実装を読むと、この文言を出しているのは Docker 自身の割り当て台帳です。したがって、誰も待ち受けていなくてもこのエラーは出ます。

誤解の提示、実装に基づく訂正、そこから導かれる帰結が1段落に収まっている。

### 原因説明

**悪い**：
> ### 原因2：ポートの競合
> 他のプロセスがポートを使用している可能性があります。確認して、必要に応じて停止してください。

状態が定義されておらず、何を見れば判断できるか書いていない。

**良い**：
> ### 原因2：Docker 以外のプロセスが待ち受けている
> 文言が `address already in use` の場合はこちらです。基本ソフトウェアが拒否しているため、必ず持ち主がいます。
> （確認コマンド）
> 持ち主が判明したら、止めるか、公開するポートを変えます。コンテナの中の待ち受けポートを変える必要はありません。変えるのはホスト側だけです。

判別条件、根拠、確認手段、対処の範囲が揃っている。

### 確認手順

**悪い**：
> ログを確認して、エラーの原因を特定します。

**良い**：
> 理由が `Failed` のイベントを探します。文言が `not found` で終わっていれば参照先が存在せず、`couldn't find key` で始まっていれば参照先はあるがキーがありません。

どこを見て、何で分岐するかが確定している。

### 根拠の示し方

**悪い**：
> 一般的に、このエラーはリソース不足が原因と言われています。

出典がなく、伝聞になっている。

**良い**：
> 公式文書によれば、既定のハード閾値は memory.available が 100Mi、nodefs.available が 10% です。実装でも、この値を割った時点で退避の対象が選ばれます。

一次資料に基づき、数値が具体的。

### Editor's Note

**悪い**：
> このエラーは多くの開発者を悩ませてきました。Docker の歴史は長く、さまざまな改善が重ねられています。今後の発展に期待したいところです。

主張がなく、根拠もない。

**良い**：
> 2022年7月の報告です。表示されたのは「コンテナは 20977608Ki を使っており、要求量 0 を超えている」という趣旨の文言でした。報告者の指摘は明快です。このコンテナは「要求量 0 を超えたから」退避されたのではない、ノードが閾値に達したから退避された、と。同じ構造の指摘は3年後にも出ています。

具体的な記録に基づき、記事の軸を裏付けている。

### 日本語

**悪い**：
> このエラーが発生した場合、まず最初に確認を行うことが重要です。設定ファイルの内容を確認することができます。

冗長、翻訳調、「確認」の反復。

**良い**：
> まず設定ファイルを見ます。ここに書かれた値と、実際に送られている値が違うことがあります。

### 境界説明

**悪い**：
> 似たエラーとして 503 もあります。こちらも確認するとよいでしょう。

違いも判別方法も書かれていない。

**良い**：
> 応答できる Pod が存在しない場合は 503 です。混雑という点では似ていますが、429 は「受け付けられない」、503 は「宛先がいない」という違いがあります。

## 11. 公開前の監査基準

### 機械的に確認する項目

- front matter 11項目がすべて存在し、途中で切れていないか
- `draft: true` が混入していないか
- `date` と `lastmod` の形式と整合（書き直しなら date が元の公開日か）
- `components` と `related_services` が空でないか
- 見出しが規定の8つで、順序どおりか
- 用語集リンクの参照先がすべて実在するか
- 記事間リンクの参照先がすべて公開済みか
- 本文字数が範囲内か（コードブロック・空白除く）
- Before/After の形式が正しいか
- コードブロックの開閉が対応しているか
- 太字の `**` が対応しているか
- 免責事項が定型どおりか
- 日本語・英数字以外の文字（他言語）が混入していないか
- 外部リンクがすべて実在確認済みのものか

### 判断が必要な項目

- **根拠不足**：各主張に対応する一次資料があるか。充足条件（公式3・実事例1・境界1）を満たすか。
- **URL と主張の不一致**：引いた資料に、実際にその記述があるか。
- **公式資料の取り違え**：別ページ・別セクションの内容を帰属していないか。
- **存在しないエラー例**：応答例のフィールドと値が実物と一致するか。
- **既存記事との重複**：扱う原因・狙うクエリが既存記事とぶつかっていないか。
- **対象範囲の曖昧さ**：冒頭で扱う現象が確定しているか。「補足」で対象外が明示されているか。
- **危険な手順**：影響範囲と条件が添えられているか。検証の無効化を無批判に勧めていないか。
- **コマンドの実行条件不足**：どの環境・どの権限で実行するかが分かるか。プレースホルダーが実値になっていないか。
- **説明の薄さ**：原因が「確認してください」で終わっていないか。出力のどこを見るかが書かれているか。
- **不自然な日本語**：語尾の反復、翻訳調、冗長表現、抽象語の放置がないか。
- **内部メモの混入**：思考過程、調査メモ、生成指示、自己評価が本文に残っていないか。
- **記事内の矛盾**：冒頭の主張と各原因の記述が一貫しているか。
- **Editor's Note の根拠不足**：実在の記録に基づいているか。日付・状態を確認したか。

## 12. Claude API 実行手順

### 調査前

1. 対象スラッグの記事が既に存在しないか確認する（出力先、公開状況）。
2. 内容が近い既存記事を特定し、扱っている原因と狙っているクエリを確認する。
3. 共食いしない切り口の仮説を立てる。立てられない場合は、その旨を報告して中止する。

### 調査中

4. エラー文言を生成している実装箇所を特定する。ここから軸を立てる。
5. 公式ドキュメントで、既定値・仕様・推奨対処を確認する。
6. 隣接するコード・状態との境界を確認する。
7. 実事例を探し、日付・クローズ状態・環境を確認する。
8. 充足条件（公式3・実事例1・境界1）を満たしたか確認する。満たせない項目は記録する。
9. 応答例・数値・文言は、すべて取得した資料と照合する。照合できないものは使わない。

### 構成作成時

10. 軸を1文で決める。全節をその軸で貫く。
11. 原因を4〜6個立て、対処が重複していないか確認する。
12. 最後の原因を、切り分けの誤りに充てるか検討する。
13. 危険な操作を含む節を特定し、警告の配置を決める。

### 本文執筆時

14. 冒頭まとめで軸と誤解の訂正を提示する。
15. 各節で、その節の目的から外れる内容を書かない。
16. 断定と留保を、根拠の強さに応じて使い分ける。
17. 用語集リンクは実在する語のみに張る。
18. 記事間リンクは公開済み記事のみに張る。

### fact-check 時

19. 各主張を、対応する資料と1対1で照合し直す。
20. 応答例のフィールドと値を再確認する。
21. Editor's Note の記録の日付と状態を再確認し、時制が正しいか確認する。
22. 冒頭の主張と本文の記述が矛盾していないか確認する。

### 最終監査時

23. 第11節の機械的項目をすべて確認する。
24. 第11節の判断項目を確認する。
25. 未確認事項が残っている場合、本文に含まれていないことを確認する。

### 出力時

**完成した Markdown 記事のみを出力する。** 以下を一切含めない。

- 思考過程・推論の記述
- 調査メモ・URL 一覧などの中間出力
- ユーザーへの説明・報告
- 「以下が記事です」などの前置き
- 自己評価・品質コメント
- 作成方針の説明
- 内部向けコメント（HTML コメントを含む）
- コードフェンスで記事全体を囲む処理

出力は front matter の `---` で始まり、免責事項の斜体行で終わる。
